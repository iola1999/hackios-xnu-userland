# rebase-26：Mesa 26.x 移植层（`REBASE=26 tools/mk-mesa.sh` 时应用）

应用顺序（在 mk-mesa.sh 的 tar 解包之后、原有 `tools/mesa/*.patch` 循环之后）：

1. 原有 `tools/mesa/*.patch` 照旧应用；在 26.2.5 上有 9 个文件的部分 hunk 失败，属预期，失败明细见顶层 `docs/analysis/mesa-rebase-2026-10.md` 第 2 节。
2. `0001-fd6-indirect-buffer-wfm-a8xx.patch`（upstream 2ee0a5e6）与 `0002-fd6-query-barriers-gen8.patch`（upstream 779cdb8e）：两个 a8xx 修复在 26.3-branchpoint 才有，26.2.5 上 cherry-pick 干净；若改用 26.3.x 基准则这两个可以去掉。
3. `0003-restore-osmesa-26.x-drift-adaptations.patch`：回滚 upstream 的 OSMesa 删除（027ccd963b）、以 25.0.7 的已打补丁版本恢复 osmesa 前后端（内容已包含 osmesa-es-profile 与 freedreno-darwin 的 osmesa hunk，因此那两个旧补丁的这些 hunk 必须处于跳过状态），并带上 26.x 接口变化的全部适配（glapi 包含路径、driParseConfigFiles 新签名、postprocess 剥离、u_sync_provider darwin 门控、libglapi_bridge 强制链接以导出 gl* 等）。
4. `0004-turnip-msm-darwin.patch`：Turnip（Vulkan）在 iOS 上经 msm 后端和 `tools/mesa/redwood-drm` 访问内核的 `RedwoodGPU`，用 `TURNIP=1 REBASE=26 tools/mk-mesa.sh` 构建。Turnip 单独构建时定义 `HAVE_LIBDRM`，Vulkan 运行时才能经 `drmGetDevices2` 找到设备；Darwin 上为 Turnip 编译 `u_sync_provider.c`；缓冲区映射改走 `redwood_drm_map`；`cache_ops_aarch64.c` 在 Darwin 上从 sysctl `hw.cachelinesize` 取缓存行大小，因为 XNU 不允许 EL0 读 `CTR_EL0`。补丁在 `REBASE=26` 时总会应用，除 `cache_ops_aarch64.c` 外，改动只在构建 Turnip 时生效。
5. `0004-a830-no-early-preamble.patch`：A830 的设备表关掉 `has_early_preamble`。开着时，片段着色器经 bindless fb-read 描述符读帧缓冲的 gallium 绘制会让 GPU 停住（CP 已取完命令，HLSQ 一直忙）；关掉后同样的绘制都能完成。实测见顶层 `docs/progress/2026-10-30-ios26-usable-desktop.md` §4.3。
6. `0005-linear-import-last-level-padding.patch`：线性导入的末级行数不是 4 的倍数时，`fd6_layout.c` 补齐后的布局可能超过 IOSurface 的分配（45x42 RGBA16Float，每行 384 字节，布局 16896 字节，分配 16384 字节）。各行都落在内存内的单级单层线性导入照样接受，资源标记 `sysmem_only`，绘制时不走 GMEM，不触及补齐的行。实测见顶层 `docs/progress/2026-10-30-ios26-usable-desktop.md` §5。
7. `0006-a830-no-fs-tex-prefetch.patch`：A830 的设备表再关掉 `has_fs_tex_prefetch`，在 0004 之后应用。开着时 ir3 把片段着色器开头直接用插值坐标的纹理读取改成着色器启动前的预取，QuartzCore 的 `glass_background_no_bleed_lph`（纹理 4、采样器 1）预取读到的距离场全为 0，Dock 玻璃的片段全部被丢弃；关掉后同一读取得到正确的距离场，Dock 与搜索栏显示完整的玻璃。上游已对 A810 与 a8xx_gen2 关掉这一项，A810 的注释写着 A830 可能也需要。实测见顶层 `docs/progress/2026-10-31-boot-order-and-performance.md`（`bo51`）。
8. `0007-ir3-retry-spilling-stage-without-preamble.patch`：用了私有内存的 stage 打印一行 `ir3[进程 pid]:`（私有内存字节数、`max_reg`、preamble 指令数，每进程前 64 行）；任务环境变量 `REDWOOD_IR3_SPILL_RETRY=1` 时，对有 preamble 的这类 stage 关掉 preamble 再编一次，私有内存更少、或私有内存相同而寄存器更少的一份胜出。不设变量时只多打印。`kernel-12377-rate1-rt1` 里这类 stage 只有 11 个，在 SpringBoard 与 iconservicesagent，backboardd 没有，重编一批没有跑。
9. `0008-u-trace-redwood-pass-times.patch`：任务环境变量 `REDWOOD_PASS_TIMES=1` 打开 Mesa 的 GPU 时间戳，按 pass 种类（画布尺寸、GMEM bin 数、颜色附件数、深度／模板格式）每 5 秒汇总一行 `pass times`；`fd_trace_read_ts` 去掉 `FD_BO_PREP_NOSYNC` 加 10 ms 睡眠的轮询，直接阻塞等待，这一处对所有打开 u_trace 的用法生效。读法见顶层 `docs/analysis/2026-11-02-120hz-after-gpu-clock.md` §6。
10. `0009-fd-resource-contents-undefined.patch`：新增 `fd_resource_contents_undefined()`，把资源标为内容无效，下一个画进它的 batch 不再把它读回 GMEM；上一个写它的 batch 照样写回。AIR 在 Metal pass 的第一次绘制前，对 `MTLLoadActionDontCare` 的颜色附件调用它。CoreAnimation 整屏 pass 的第二个 RGBA16Float 附件属于这种情况，此前每个 bin 都读回，见顶层 `docs/analysis/2026-11-02-120hz-after-gpu-clock.md` §6。
11. `0010-fd-no-store-of-masked-cbufs.patch`：batch 结束时不写回绑定的混合状态写不到的颜色附件（`colormask` 为 0）。混合状态变化也触发附件的读写登记，写不到的附件按读入登记。CoreAnimation 整屏 pass 的颜色 1 由管线的 `writeMask 0` 关掉，此前每个 bin 都写回。`kernel-12377-rate8-ns1` 对 r8a：tile store 合计 3.33 → 2.76 s，整屏 pass 每次 808 → 787 µs，手势帧率在轮次间波动范围内，截图无差异，见顶层 `docs/progress/2026-11-05-defaults-and-charging.md`。
12. `0011-fd-shared-no-shadow.patch`：freedreno 不再对导入的资源（`fd_resource_from_handle` 置 `is_shared` 的那些）做 shadow。shadow 会换掉资源的 bo 并在批次结束后释放旧 bo，而 AIR 对导入的缓冲只在创建时映射一次，换 bo 之后它写的是驱动要释放的内存；`util_copy_rect` 行拷贝里的 SIGSEGV 由此而来，补丁说明记了两轮的崩溃地址与拷贝长度。
13. `0012-fd-shadow-guard-probes.patch`：诊断用。`freedreno_resource.c` 统计 shadow 的调用、拒绝与换 bo 次数，第一次拒绝、第一次换 bo 和进程退出时各打一行 `rwa shadow:`；`u_format.c`、`u_surface.c`、`u_transfer.c` 和 `freedreno_resource.c` 的拷贝与映射处调用 `tools/mesa/air/air_metal.c` 的 `rwa_*_guard`，指针不可能是地址时打一行，拷贝记录写进 AIR 库的环形缓冲，进程收到 SIGSEGV 时打印。
14. `0013-fd-transfer-stride-after-shadow.patch`：`fd_resource_transfer_map` 在 shadow 成功后按新布局重取 `stride` 与 `layer_stride`。传输的 stride 在调用 shadow 之前就从旧布局取好了，不重取时映射偏移和调用方逐行拷贝用的是两套布局。
15. `0014-perf-probes-26.x.patch`：旧的 `draw-perf*.patch`、`fd-*.patch`、`fd6-*.patch`、`perf-*.patch` 在 26.2.5 上部分 hunk 失败，这个补丁补齐真机库里的状态：`fd_bo_cpu_prep` 与 `fd_perf_us` 只在 `FD_PERF_DRAW=1` 时计时；`fd6_draw.cc` 按段计时，超过 50 ms 的段打 `fd draw seg slow`；批次切分计数；定义旧补丁只声明的 `fd_perf_cache_misses`（缺了它库链接不过）；去掉 `ir3_cache.c` 里重复的一次未命中计数。
16. `0015-fd-bo-heap-null-check.patch`：`fd_bo_heap_alloc` 在 `calloc`、`fd_bo_new` 或 `fd_bo_map` 返回 `NULL` 时释放已持有的锁与引用并返回 `NULL`，防止分配或映射失败时解引用空指针。

`rebase-26/` 下的补丁按文件名顺序应用。两个 `0004` 开头的补丁分别来自 Turnip 与 A830 两条工作，改的文件互不重叠。打完这一层的源码树，加上 `tools/mesa/redwood-drm` 与 `tools/mesa/air`，就是真机 AIR 库的构建源；`PREPARE=1 VERSION=26.2.5 SHA256=… REBASE=26 tools/mk-mesa.sh` 只做到这一步，arm64e 构建见顶层 `tools/k90auto/setup-mesa-arm64e.py`。

`smoke-osmesa.c` / `smoke-osmesa-es.c` 是构建后冒烟测试，在 macOS 主机上编译运行，见顶层 `docs/analysis/mesa-rebase-2026-10.md` 第 3 节。
